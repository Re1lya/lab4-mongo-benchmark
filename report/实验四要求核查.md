# 实验四 要求核查

逐条对照《实验四：MySQL 与 MongoDB 日志读写性能对比实验》指导书，列出本组的实现位置和证据。

## 一、实验目的

| 要求 | 本组实现 | 证据 |
| --- | --- | --- |
| 掌握 Spring Data JPA 访问 MySQL、Spring Data MongoDB 访问 MongoDB，完成日志写入和条件分页查询 | `logdemo-jpa`（`LogPo`、`LogPoMapper extends JpaRepository`）；`logdemo-mongo`（`LogDoc`、`LogDocMapper extends MongoRepository`） | 部署后 22 项接口检查两边全部通过：`results/00-环境与一致性/api-compare.md` |
| 同一套日志业务模型、接口定义、请求数据和测试方法，对照实现两条链路 | 共用模块 `logdemo-core`：同一个 Controller、Service、`LogRecord` 模型和校验；两种实现只替换 `LogStore` | 两种实现逐项比较“全部一致”；同一份 JMX 与请求数据；预置数据内容摘要相同（`digest-*.json`） |
| 使用 JMeter 和 Prometheus 做负载测试和压力测试 | 第 1 轮梯度探索：负载测试 10/25/50/100 线程、压力测试 200/300/400 线程，加 10 线程恢复检查。第二阶段：固定参数的主对比 3 轮（查询 50、写入 100 线程，每次 240 秒，统计第 60～240 秒），MongoDB j:true 持久性对照，并发量调优 25～150 线程，连接池调优 25/50/100，600/800/1000 线程过载与恢复。第三阶段（11-19）：按老师更新的监控配置复测主对比与 j:true，逐级加压找最多同时运行线程数（查询 400、写入 2000），并在该线程数下持续压测。Prometheus 第一、二阶段每 2 秒抓取应用与 5 台机器指标；第三阶段节点每 1 秒采集、CPU 使用率取 2 秒平均（规则每 2 秒计算） | `results/r1/`、`m1/`～`m3/`、`sweep/`、`pool/`、`overload/`、`n1/`、`probe/`、`x1/`（每次测试的 JTL、参数、起止时间、监控时间序列）；`results/统计与图表/` |

## 三、日志数据模型与数据库格式

| 指导书要求 | 本组实现 |
| --- | --- |
| logId 为业务主键，26 位 ULID 或 32 位 UUID | 26 位 ULID，程序生成（`Ulid.java`，含已知向量单元测试）；MySQL `CHAR(26)`（ascii_bin），Mongo `_id` 字符串 |
| createdAt 统一以 UTC 保存 | MySQL `DATETIME(6)` + 会话时区 UTC；Mongo BSON Date；统一截断到毫秒，两库存值相同（实测） |
| message 不超过 4096 字符 | 程序按 Unicode 码点校验；MySQL `VARCHAR(4096)`；Mongo `$jsonSchema maxLength: 4096`；接口检查覆盖 4096/4097 边界 |
| 表 2 字段：id、traceId、level、source、message、clientIp、createdAt | 字段、类型、长度与表 2 一致：`db/mysql/01-schema.sql`、`db/mongo/01-init.js` |

## 四、统一 REST API

| 指导书要求 | 本组实现 |
| --- | --- |
| `POST /api/logs`，JSON 日志对象，单条写入 | 成功返回 HTTP 201、`errno=1`；校验失败返回 400、`errno=3` |
| `GET /api/logs`，参数 level、from、to、page、size，按级别和时间范围分页查询 | 时间范围 [from, to)，按 createdAt、id 倒序，page 从 1 开始，size 1–100；成功返回 HTTP 200、`errno=0` |
| JMeter 只替换 host 和端口，不改请求体、断言或线程组 | `WriteLog.jmx`、`ReadLog.jmx` 两种实现共用，只通过 `-Jport=8081/8082` 区分 |
