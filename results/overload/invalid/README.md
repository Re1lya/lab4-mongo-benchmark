# 无效的一次测试（保留原始数据）

`jpa-read-overload-t800` 与紧接其后的 `jpa-read-recovery800-t10`（2026-11-16 20:05–20:13，JMeter 在 CDWY4）。

这次 800 线程测试中，压测机自身成了瓶颈：统计区间内平均 701 个活跃线程、平均响应 258 ms，按“线程数 ÷ 吞吐量 − 平均响应时间”估算，
JMeter 在两次请求之间平均要额外花 577 ms（其余各次测试都在 0.15 ms 以内），吞吐量只有 839 次/秒，最后一个线程比设定的升压时间晚约 70 秒才启动。
测试期间 CDWY4 的 JMeter 进程占满 2 个核、运行队列长达数百，而被测服务远未饱和，所以结果不能代表 MySQL 版在 800 线程下的表现。
恢复检查的前提（刚经历 800 线程过载）也不成立。

两者已在全部测试结束后按同样步骤重测（预热 120 秒 → 800 线程 → 间隔 30 秒 → 10 线程恢复检查），重测结果在上一级目录。
