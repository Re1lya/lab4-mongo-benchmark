## 遇到的问题与解决

**1. 服务器之间、服务器与本机都不能用密码脚本登录。**
用一把实验专用密钥（`ssh-copy-id` 一次性安装），之后所有操作都免密。数据库、应用的密码由脚本在服务器上随机生成，存进 Docker secret，任何文档和仓库里都没有密码。

**2. CDWY5 无法加入 Swarm。**
连通性测试：CDWY5 → CDWY1 的 2377/7946 超时（被拦截），22/3306/8080 可达。原因是 CDWY5 与另外 4 台不在同一安全组。在控制台调整安全组后再测，全部端口可达，顺利加入。
附带问题：全局服务 node-exporter 的镜像只存在于各节点本地，新节点上没有。先从 CDWY1 导出镜像传到 CDWY5，避免任务反复失败。

**3. 服务器拉不到 MongoDB 7.0 镜像。**
服务器访问 Docker Hub 超时；课程 SWR 仓库的 `mongo:latest` 实际是 8.0.9，不符合指导书“Mongo 7.0”。在本机查出官方 `mongo:7.0` 的 amd64 镜像摘要，在 CDWY5 上**按摘要**从镜像站拉取。Docker 会校验摘要，所以内容与官方完全一致，版本为 7.0.48。

**4. Prometheus 抓不到新服务（HTTP 400）。**
在 Prometheus 容器里 `wget http://lab4_logjpa:8080/...` 返回 400。原因：Swarm 服务名带下划线，不是合法主机名，Tomcat 直接拒绝这样的 Host 头。实验三能用 `productdemoaop:8080`，正是因为那个名字没有下划线。改为抓取 `172.31.1.202:8081/8082` 后正常。
另外，现有 Prometheus 开启了 basic auth。为了不在脚本里使用账号密码，导出数据改用 `promtool tsdb dump` 读取 TSDB 快照。

**5. 第一次预试验，50 线程只有约 700–800 次/秒。**
随后的探测里，同一服务在 400 线程下达到约 3300 次/秒。原因是 JVM 冷启动：JIT 还没编译热点代码。正式测试因此每组先预热 60 秒，并在每轮开始时重启服务，保证起点一致。

**6. 压测机（CDWY3）资源紧张。**
CDWY3 上有课程以外的 rbac 服务，只剩约 550MB 内存；今天早些时候运行 `jmeter --version` 就因默认 1GB 堆申请失败而崩溃（`/root/hs_err_pid31965.log`）。`run-test.sh` 把 JMeter 堆限制为 400MB；800 线程试跑时可用内存降到约 220MB，所以压力测试最高定为 400 线程。另外，JMeter 5.6 的“持续时间”从每个线程启动时算起，线程启动慢时实际并发会低于设定值，统计时用“稳态”口径（全部线程都在运行的时间段）。

**7. JTL 文件太大。**
默认 JTL 保存 URL，查询请求的 URL 很长，一次 60 秒测试约 40MB。关闭 URL、数据类型等用不到的字段后约减半；入库时再用 gzip 压缩。

**8. 导出 Prometheus 数据的几个小坑。**
`promtool tsdb dump` 要把数据块硬链接到临时目录，临时目录必须和数据在同一文件系统，并且事先存在；Prometheus 镜像默认以 nobody 用户运行，对 root 所有的快照目录没有写权限。最后做法：复制快照 → 在快照里建临时目录 → 以 root 运行一次性的 promtool 容器。
另外，MongoDB 驱动的连接池指标带 `cluster_id` 标签，服务每重启一次就变一次，同一指标会拆成多条序列，统计时要合并。用相邻抓取的差值算速率时，要除以第一个到最后一个样本的实际时长，不能除以整个窗口长度，否则会偏低几个百分点。改正后，服务端与 JMeter 的吞吐量偏差不超过 1%。

**9. 测试后恢复实验三应用时，CDWY1 内存吃紧。**
实验三应用（约 570MB）与实验四两个服务（各约 300MB）同时运行时，CDWY1 可用内存降到约 77MB，有触发 OOM 的风险（同机还有课程外的 `demo` 容器）。压测已结束，因此把实验四的两个服务缩到 0，可用内存回到约 980MB。数据保存在 MySQL 和 MongoDB 中，需要演示时按操作手册第 9 节启动。
另外，在 CDWY1 上 `curl localhost:8080` 会先解析成 IPv6 的 `::1`，而 Swarm ingress 只转发 IPv4，表现为连接超时；改用 `127.0.0.1:8080` 正常。

**10. 本机 zsh 不对变量分词。**
`set -- $spec` 在 zsh 里不会拆分，导致第一次预试验参数错位、一个请求都没发出。改用 `${=spec}`。

**11. 第二阶段要跑约 6 小时，客户端中途可能关机。**
编排脚本原来在客户端运行、经 SSH 向各服务器下发命令，客户端一关机测试就中断。改法：
（1）脚本可续跑：已完成的测试（有 `end.txt` 且 JTL 非空）自动跳过；`run-test.sh` 重跑同一目录前先删掉旧文件（JMeter 的 `-l` 是追加写入）。
（2）编排放到 CDWY4，用 `nohup setsid` 在后台运行，出错 60 秒后从断点重试。
（3）服务器之间登录用一把只为这次测试生成的密钥，`authorized_keys` 中限制只能从 CDWY4 内网地址登录（`from="172.31.1.19"`）、禁止各种转发；测试全部完成后由脚本自动删除。
切换过程：客户端跑完主对比第 1 轮 MySQL 写入后，在下一次预热刚开始时停掉客户端编排和 CDWY3 上的 JMeter，再在 CDWY4 启动；已完成的 3 项被自动跳过，预热重新开始。新版脚本先写到别处，等旧实例停掉后才替换：bash 边读边执行，原地覆盖正在运行的脚本会让它读到错位的内容。

**12. 过载阶段在 CDWY4 上启动不了 JMeter，测试停了约 5 小时。**
现象：日志中“CDWY4 JMeter：”后面是空的，随后预热立即失败，`run-all.sh` 重试 3 次后输出 `SUITE-FAILED`。
原因：CDWY3 上的 `/opt/jdk-21` 是指向 `/opt/java/amazon-corretto-21…` 的符号链接，脚本只打包了 `jdk-21` 这个链接，没有打包它指向的目录，CDWY4 上得到的是一个悬空链接。
处理：经内网把 `/opt/java/…` 目录复制到 CDWY4，`java -version`、`jmeter --version` 正常后从断点续跑；脚本改为同时复制链接和实际目录，并且版本检查为空时明确报错。
教训：试运行没有覆盖“首次复制 JDK”这一步（试运行时没有跑到过载阶段）；无人值守运行前，应把每个阶段的准备步骤都单独试一遍。本机的守望脚本只在本机开着时有效，这次关机期间没人处理失败。

**13. 过载测试中有一次压测机自身成了瓶颈。**
MySQL 版查询 800 线程那次只有 839 次/秒，测试时长拉到 5 分 53 秒，最后一个线程比设定的升压时间晚约 70 秒才启动。当时 CDWY4 上的 JMeter 占满 2 个核、运行队列长达数百。用“线程数 ÷ 吞吐量 − 平均响应时间”估算，JMeter 在两次请求之间平均多花 577 ms（其余各次都在 0.15 ms 以内）。处理：这项指标加进统计脚本（`client_gap_ms`），作为每次测试的压测机自检；该次结果移到 `results/overload/invalid/`，全部测试结束后按同样步骤重测。

**14. 查询测试前没有重置数据库。**
写入测试前会重置两个库，但写入的数据会留到下一次重置。因此主对比中 MySQL 第 3 轮、MongoDB 第 2 轮的查询，是在库里多出约 100 万条日志的情况下进行的，吞吐量比另两轮低 3%～6%；MySQL 第 3 轮的预热只有 720 次/秒（缓冲池被新写入的数据页占满）。新写入的日志不在查询时间范围内，结果集不变。报告中如实说明，并发量调优与连接池调优的对照点取数据库状态相同的那一次测试。改进：每次查询测试前也重置数据库。

**15. MySQL 版连接池的实际连接数多次少于设定值，高并发查询结果不稳定。**
监控显示 HikariCP 的连接数在测试中多次只有 73、58 个，空闲时最低 24 个，再逐个补足；MongoDB 驱动的连接池一直保持设定值。MySQL 版查询在 75 线程以上多数时候只有 2,000～2,700 次/秒（应用服务器先饱和），但过载 600、1000 线程两次约 3,200 次/秒。推测与 Swarm 虚拟 IP（IPVS）断开空闲连接有关，未验证；报告中作为局限说明。
11-17 检查 binlog 时发现后果更严重：MySQL 连接数已达上限 300，其中 `lab4app` 290 个、rbac 10 个，“连接数已满被拒绝”的计数几分钟内增加了 32 次，rbac 换新连接时随时可能被拒。`lab4app` 的会话全部是 Sleep，其中多数空闲 15 分钟以上：连接池关闭这些连接时，因 IPVS 已断开连接，MySQL 收不到，旧会话约 2 小时后才被回收，而连接池又不断新建连接。处理：
（1）只清理 `lab4app` 空闲超过 30 分钟的会话（191 个；连接池在用的连接不会空闲这么久），rbac 的会话不动，连接数 301 → 110；
（2）给 `lab4_logjpa` 加 `SPRING_DATASOURCE_HIKARI_KEEPALIVETIME=300000`，让连接池每 5 分钟给空闲连接发一次保活，空闲连接不再被 IPVS 断开；重启后清掉旧容器留下的 83 个失效会话（全部空闲 16 分钟以上）；部署文件同步加上这一项；
（3）观察 10 分钟：`lab4app` 稳定在 100 个，最长空闲 86～145 秒，rbac 10 个，被拒连接不再增加。

**16. MySQL binlog 累计约 14 GB。**
测试结束时 CDWY2 上 MySQL 共有 14 个 binlog 文件、约 14 GB（`binlog_expire_logs_seconds` = 30 天），磁盘已用 64%、剩余约 14 GB。这台 MySQL 与 rbac 服务共用。
11-17 经同意后清理。先确认没有东西依赖这些文件：没有注册的从库、没有 binlog 转储线程、本机不是从库、GTID 关闭；除 root 外没有账号有复制权限（rbac 的账号只能增删改查自己的库）；5 台服务器都没有备份或订阅 binlog 的定时任务和进程。清理 binlog 不改动任何表，rbac 的数据不受影响。为保险起见，先用 `mysqldump --single-transaction`（不锁表）导出 rbac 的两个库 `unified_permission`、`rbac_migration_20261022`，存为 CDWY2 的 `/root/rbac-backup-20261117.sql.gz`（仅 root 可读，76 张表齐全）。然后执行 `PURGE BINARY LOGS TO 'binlog.000021'`，删除 `000008`～`000020` 共 13 个文件，只保留正在写的一个；磁盘已用从 24 GB（64%）降到 11 GB（28%）。

**17. 按组内要求暂停 rbac。**
rbac 是课程以外的服务，此前约定不动；11-19 组内说明 rbac 之后要更新后重新部署，要求先暂停，避免影响实验。服务器上属于 rbac 的有两部分：Swarm 服务 `rbac_backend`（运行在 CDWY3）和 CDWY3 上调用它的 OIDC 客户端 systemd 服务 `unified-permission-clients`。前者缩到 0 个副本（配置保留），后者 `systemctl stop`（仍为开机自启）。各服务器上的 `uniagent` 是华为云的监控代理，不属于 rbac，没有动。暂停后 CDWY3 可用内存从 765 MB 升到 1355 MB，第三阶段全部测试回到指导书规定的 CDWY3 发压。

**18. 按老师的新要求修改 Prometheus。**
实验三沿用的规则文件里，CPU 使用率 `node:cpu_usage_percent` 用 `rate(...[5m])`，规则组每 30 秒计算一次：一次几分钟的测试会和前后的空闲、准备时段混在一起平均。按老师 11-19 的要求改为：全局每 1 秒采集（`scrape_interval: 1s`）、每 2 秒计算（`evaluation_interval: 2s`），CPU 公式改为 `[2s]`，两个规则组的 `interval: 30s` 也改为 2 秒（组上的设置会覆盖全局）。`rate` 的窗口里至少要有 2 个样本，所以 2 秒窗口必须配合每 1 秒采集。两个日志服务仍按各自设置每 2 秒抓取一次，与其他组相同。规则文件是 Windows 换行，第一次用 `sed` 没有匹配上 `interval: 30s` 那几行，检查后补改。改完用 `promtool check` 校验并热加载，抽查确认节点样本间隔 1.0 秒、规则每 2.0 秒一个值。

**19. 逐级加压时，查询的两级压测机自身成了瓶颈。**
MySQL 版查询 800 线程、MongoDB 版查询 1200 线程两级没有通过：JMeter 同时运行的线程最多只有 643、573 个，每秒只发出约 870～930 个请求，整级持续 5～9 分钟（计划 2 分多钟）。监控显示这两级开始后不久，CDWY3 的 CPU（2 秒平均）升到 100%（用户态约 97%）并保持到结束，应用服务器 CDWY1 只有约 30%。JMeter 日志显示新线程启动被拖慢：800 个线程用了约 3 分钟才全部启动，先启动的线程到时就结束，所以同时运行的线程达不到设定值。同样 768 MB 堆，写入 2000 线程时压测机 CPU 不到 50%；查询响应平均 11.2 KB，是写入的 13 倍。没有记录 JMeter 的垃圾回收日志，具体原因未确认。
处理：按规则在第一个不通过的级别停止，查询取两种实现都通过的 400 线程；报告中说明这是 2 核压测机的上限，不是数据库的上限。改进：要测更高的查询并发，需要更强的压测机或多台压测机（JMeter 分布式），并打开 JMeter 的 GC 日志。

**20. MongoDB 版查询 400 线程那一级吞吐量偏低。**
只有 1,729 次/秒，低于紧接着的 800 线程（2,949 次/秒）和之后持续压测的 400 线程（3,430 次/秒）。当时应用服务器 CPU 已到 98%，每个请求的应用端 CPU 时间是另两次的 1.7～2.1 倍。这一级距 j:true 测试后重启 MongoDB 日志服务约 11 分钟，测前只预热了 60 秒（逐级加压每种实现只在开始前预热一次），推测服务还没有充分预热。逐级加压只判断全部线程能否同时运行，这一级通过，不影响选择；吞吐量比较以持续压测为准。改进：切换配置、重启服务之后，按正式测试的标准预热 120 秒。
