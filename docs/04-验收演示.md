# 实验四 验收演示手册

思路和实验三一样：**现场改压测参数 → JMeter 结果和 Prometheus 曲线跟着变 → 用实测数据解释原因**。实验四多了一个维度：同样的参数，只把端口从 8081（MySQL 版）换成 8082（MongoDB 版），曲线会怎么变。

## 1 为什么有两套实现（开场先讲清楚）

指导书要求“使用同一套日志业务模型、接口定义、请求数据和测试方法，对照实现 JPA/MySQL 与 Spring Data MongoDB/MongoDB 两条日志读写链路”，提交要求里也写明“仓库中应包含两套实现”。所以：

- **同一个接口**（`POST /api/logs`、`GET /api/logs`）、同一份业务逻辑和校验（`logdemo-core`），只是**数据存在哪里不同**；
- `logdemo-jpa` 用 Spring Data JPA 存 MySQL，`logdemo-mongo` 用 Spring Data MongoDB 存 MongoDB；
- 这样才能回答实验要问的问题：**同样的日志读写，MySQL 和 MongoDB 谁快、为什么快、瓶颈在哪**。JMeter 脚本也是同一份，只换端口。

## 2 演示前准备（提前 10 分钟）

1. **确认实验四服务在运行**（CDWY1）。实验三应用已停用（0 个副本），两个实验四服务一直开着：

   ```bash
   docker service ls | grep lab4
   curl -s 127.0.0.1:8081/actuator/health; curl -s 127.0.0.1:8082/actuator/health   # 都应为 UP
   ```

2. **预热**（CDWY3）：两个服务各跑一次，JVM 冷启动会慢 4～5 倍，不预热现场数字会偏低。

   ```bash
   source /etc/profile.d/lab3-tools.sh; cd /root/lab4/jmeter
   bash run-test.sh ReadLog  172.31.1.202 8081 50 5 40 /root/lab4/demo/warm-jpa
   bash run-test.sh ReadLog  172.31.1.202 8082 50 5 40 /root/lab4/demo/warm-mongo
   ```

3. **打开 Prometheus**：浏览器访问 CDWY4 的 9090 端口并登录（打不开时用 SSH 隧道：`ssh -L 19090:127.0.0.1:9090 root@<CDWY4 公网地址>`，再访问 `http://localhost:19090`）。在 Graph 页依次填入第 5 节的查询，时间范围选 15m。
4. 准备两个终端：CDWY3（跑 JMeter）、CDWY1（`docker service ls`）。需要查库时再开 CDWY2、CDWY5。

## 4 改什么、看什么（现场演示的核心）

以下命令都在 CDWY3 的 `/root/lab4/jmeter` 下执行。参数依次为：测试计划、主机、**端口**、**线程数**、**升压秒数**、**持续秒数**、输出目录；轮次用环境变量 `LOOPS`。

| 改什么 | 命令示例 | JMeter 结果会怎样 | Prometheus 曲线会怎样 |
| --- | --- | --- | --- |
| **端口（换实现）** | `bash run-test.sh ReadLog 172.31.1.202 8081 50 5 30 /root/lab4/demo/a` 后把 8081 改成 8082 | 查询：MySQL 约 3,300 次/秒，MongoDB 约 3,700 次/秒（主对比） | **跑满的机器换了**：MySQL 版是 CDWY2（数据库）CPU 约 100%、CDWY1 约 80%；MongoDB 版是 CDWY1（应用）约 99%、CDWY5 只有约 73% |
| **线程数** | 把 50 改成 10，再改成 200 | 10→50 吞吐基本不涨，平均响应和 P95 随线程数上升；线程很多时（报告中 400 线程）MySQL 版吞吐反而下降约 30% | 请求速率到顶后变平；P95 曲线抬高；线程很多时 MySQL 版 `hikaricp_connections_pending` 升到约 100（连接池排队） |
| **读→写** | `bash run-test.sh WriteLog 172.31.1.202 8081 10 5 30 /root/lab4/demo/w1`，再换 8082 | 10 线程写入：MySQL 约 1,600 次/秒，MongoDB 约 5,000 次/秒以上 | CDWY2 磁盘写入约 3000 次/秒，CDWY5 只有约 35 次/秒（MySQL 每次提交刷盘，MongoDB 批量写日志） |
| **升压时间** | 把升压 5 改成 30 | 全程平均值变化，稳态值不变 | 请求速率、CPU 曲线的**上升斜坡变长** |
| **持续时间** | 把 30 改成 60 | 样本数翻倍 | 平台段变长 |
| **轮次** | `LOOPS=20 bash run-test.sh ReadLog 172.31.1.202 8081 10 5 60 /root/lab4/demo/l` | 总请求数 = 线程 × 轮次 = 200，几秒就结束 | 曲线只出现一个很窄的尖 |

讲解要点：线程数是“同时在发请求的虚拟用户数”，不是每秒请求数；吞吐量封顶后，再加线程只会排队变慢——这就是从负载测试进入压力测试。

**改服务端配置**（CDWY1 执行，滚动重启约 30 秒，之后先预热再测；演示完改回默认值）：

| 改什么 | 命令 | 预期 |
| --- | --- | --- |
| MongoDB 写关注改为 j:true | `docker service update --env-add LOGDEMO_MONGO_JOURNAL=true lab4_logmongo` | 日志中出现 `writeConcern={"w": 1, "j": true}`；100 线程写入吞吐量降约 13%（报告 5.3 节），CDWY5 每秒写盘次数明显上升 |
| 连接池上限改为 25 | `docker service update --env-add LOGDEMO_POOL_MAXSIZE=25 lab4_logjpa` | 日志中 `pool max-size=25`；`hikaricp_connections_active` 最高到 25，并发高时 `hikaricp_connections_pending` 上升（连接池排队） |
| 改回默认值 | `--env-add LOGDEMO_MONGO_JOURNAL=false`、`--env-add LOGDEMO_POOL_MAXSIZE=100` | 恢复到主对比的配置 |

查看生效的设置：`docker logs $(docker ps -q --filter name=lab4_logmongo) 2>&1 | grep 'settings'`。

## 5 Prometheus 查询（复制到 Graph 页）

```promql
# 两种实现的每秒请求数（与 JMeter 吞吐量对得上）
sum by (impl) (rate(http_server_requests_seconds_count{uri="/api/logs"}[15s]))

# P95 响应时间（秒）
histogram_quantile(0.95, sum by (le, impl) (rate(http_server_requests_seconds_bucket{uri="/api/logs"}[15s])))

# 各服务器 CPU 使用率（%，记录规则）：172.31.1.202=CDWY1 应用，.8.46=CDWY2 MySQL，.13.151=CDWY5 MongoDB，.12.156=CDWY3 JMeter
node:cpu_usage_percent
# 即 (1 - Σrate(idle[2s]) ÷ Σrate(全部[2s])) × 100：老师 11-19 更新后的 2 秒平均（原来是 5 分钟平均），每 1 秒采集、每 2 秒计算

# 连接池：占用与排队
hikaricp_connections_active
hikaricp_connections_pending
mongodb_driver_pool_checkedout

# 数据库服务器每秒写盘次数（写入测试时看）
rate(node_disk_writes_completed_total{job="node",device="vda",instance=~"172.31.8.46:9100|172.31.13.151:9100"}[15s])
```

## 6 现场查数据（证明“写进去了、两边一样”）

```bash
# CDWY3：同一条日志分别写入两种实现，再按时间范围查出来
for p in 8081 8082; do
  curl -s -X POST 172.31.1.202:$p/api/logs -H 'Content-Type: application/json' \
    -d '{"level":"ERROR","source":"demo","message":"验收演示","clientIp":"10.0.0.8","createdAt":"2030-01-01T08:00:00+08:00"}'; echo
  curl -s "172.31.1.202:$p/api/logs?level=ERROR&from=2030-01-01T00:00:00Z&to=2030-01-02T00:00:00Z&page=1&size=5"; echo
done
```

预期：两个端口都返回 201 和 200，`createdAt` 都被换算成 `2030-01-01T00:00:00Z`（UTC）。

```bash
# CDWY2：MySQL 中的行数
docker exec $(docker ps -q --filter name=lab_mysql) sh -c 'MYSQL_PWD="$MYSQL_ROOT_PASSWORD" mysql -uroot -e "SELECT COUNT(*) FROM lab4_log.log_record"'
# CDWY5：MongoDB 中的文档数
docker exec $(docker ps -q --filter name=lab4_mongo) sh -c 'mongosh --quiet -u root -p "$(cat /run/secrets/lab4_mongo_root_password)" --authenticationDatabase admin lab4_log --eval "db.log_record.countDocuments()"'
```

写入测试前后各查一次，新增行数应等于 JMeter 里 HTTP 201 的请求数（正式测试 18 次全部相等）。

## 7 可能被问到的问题（简答）

- **为什么 MongoDB 写入快这么多，公平吗？** 主要是持久化策略不同：MySQL 默认每次提交把 redo log 和 binlog 刷盘，提交返回后数据一定不丢；MongoDB 单机默认写关注 w:1，约 100 ms 批量刷日志，宕机可能丢最近约 100 ms 的写入。两台数据库服务器每秒写盘次数相差约 60 倍就是证据。我们也测了“同等持久性”：给 MongoDB 加 `j:true` 后每秒写盘升到约 640 次，吞吐量降 13%，仍是 MySQL 的 1.58 倍——100 个并发写入共享同一次日志同步（平均每次写盘约 9 条）。
- **查询为什么也是 MongoDB 快？** 同样的查询，MongoDB 服务器每个请求耗 CPU 约 0.40 ms，MySQL 约 0.61 ms；所以 MySQL 版先把数据库机 CPU 用满，MongoDB 版先把应用机 CPU 用满。
- **负载测试和压力测试怎么区分？** 主对比（查询 50、写入 100 线程）是负载测试：在吞吐量接近最高、响应时间较低的并发量下比较两种实现；逐级加压（400～2000 线程）和最多线程数下的持续压测是压力测试：看超出处理能力时的表现——不报错、排队变慢（平均响应时间约等于线程数 ÷ 吞吐量），撤压后紧接的 10 线程恢复检查立即回到几毫秒。
- **怎么保证比较公平？** 同一份代码（只换持久层）、同一份 JMX 和请求数据、同样的预置数据（两库导出摘要相同）、连接池等配置相同、两种实现依次执行、每项测试前重置两库（查询也重置）、每次测试前单独预热、固定统计第 60～240 秒。另外每次测试都做压测机自检，确认 JMeter 不是瓶颈（逐级加压中查询的两级正是因为压测机先到上限而判为不通过）。
- **怎么证明数据没丢？** 15 次有入库核对的写入测试，JMeter 成功数与数据库新增行数逐次相等；26 次测试中 JMeter 与 Prometheus 服务端统计的吞吐量偏差不超过 0.4%。
- **为什么 id 用 ULID？** 26 位、按时间有序，MySQL 聚簇索引顺序插入，MongoDB 直接当 `_id`；指导书建议 26 位 ULID 或 32 位 UUID。
