两套服务**共用同一份接口、业务逻辑和校验**（`logdemo-core`），只有持久层不同：

| 层 | 共用（logdemo-core） | MySQL 版（logdemo-jpa） | MongoDB 版（logdemo-mongo） |
| --- | --- | --- | --- |
| 接口 | `LogController`：`POST /api/logs`、`GET /api/logs` | — | — |
| 业务 | `LogService`：生成 ULID、补全时间和 IP、参数校验 | — | — |
| 持久层接口 | `LogStore`（insert / find） | `JpaLogStore` | `MongoLogStore` |
| 数据对象 | `LogRecord` | `LogPo`（`@Entity`） | `LogDoc`（`@Document`） |
| Repository | — | `LogPoMapper extends JpaRepository` | `LogDocMapper extends MongoRepository` |

这样做的好处：两边的差异只剩“怎么存、怎么查”，性能对比才公平；JMeter 脚本只换端口。

## 2 Spring Data：一套写法，两种数据库

Spring Data 把数据访问抽象成 **Repository 接口**，你只写接口，框架生成实现。

| 写法 | JPA（MySQL） | MongoDB |
| --- | --- | --- |
| 继承的接口 | `JpaRepository<LogPo, String>` | `MongoRepository<LogDoc, String>` |
| 自定义查询 | `@Query("select l from LogPo l where l.level = :level and l.createdAt >= :from and l.createdAt < :to")`（JPQL） | `@Query("{ 'level': ?0, 'createdAt': { '$gte': ?1, '$lt': ?2 } }")`（查询文档） |
| 分页排序 | 参数 `Pageable` → `ORDER BY ... LIMIT ?,?` | 参数 `Pageable` → `sort().skip().limit()` |

**返回 `List` 还是 `Page`？** 返回 `Page` 时框架会多执行一次 `count` 统计总数；日志表很大时，计数往往比查 20 条还慢。本实验接口只返回 `list/page/pageSize`（与课程仓库的 `PageDto` 一致），所以 Repository 返回 `List`，不做计数。

**坑：** Spring Data MongoDB 的派生方法名里同一个字段出现两次（`findByCreatedAtGreaterThanEqualAndCreatedAtLessThan`）会报错，所以 Mongo 版用 `@Query` 显式写查询（`LogDocMapper.java`）。

## 3 实体与文档：几个容易忽略的细节

**JPA 的 `save()` 可能先 SELECT 再 INSERT。** 主键由程序预先生成（ULID）时，Spring Data 看到 id 不为空，会认为对象“已存在”，调用 `merge()`：先按主键查一次，再插入。解决办法是实现 `Persistable` 的 `isNew()`，告诉框架这是新对象（`LogPo.java`）。这样每次写入只有一条 INSERT。

**Mongo 用 `insert()` 而不是 `save()`。** `save()` 是“按 `_id` 替换，不存在才插入”（upsert），语义和开销都不同（`MongoLogStore.java`）。

**去掉 `_class` 字段。** Spring Data MongoDB 默认在每个文档里写入实体类全名，用于多态映射。本集合只有一种文档，`MongoConfig` 把它关掉；集合的 `$jsonSchema` 校验器也设置了 `additionalProperties: false`，多余字段会被拒绝。

**id 直接作为 `_id`。** `@MongoId(FieldType.STRING)` 让 ULID 字符串原样保存，不转换成 ObjectId。

## 4 表结构与数据校验

| 约束 | MySQL（`db/mysql/01-schema.sql`） | MongoDB（`db/mongo/01-init.js`） | 程序（`LogVo`） |
| --- | --- | --- | --- |
| 必填 | `NOT NULL` | `$jsonSchema.required` | `@NotBlank` |
| level 取值 | `CHECK (level IN (...))` | `enum` | `@Pattern` |
| 长度 | `VARCHAR(n)` | `maxLength` | `@MaxCodePoints` / `@Size` |
| 类型 | `DATETIME(6)` | `bsonType: 'date'` | `Instant` |

三层都校验：程序层给出友好的错误信息（HTTP 400），数据库层兜底，保证脏数据进不了库。

**“4096 个字符”怎么数？** MySQL `VARCHAR(4096)` 按字符（Unicode 码点）计数；Java 的 `String.length()` 按 UTF-16 单元计数，一个 emoji 算 2。所以 message 的上限用码点数判断（`MaxCodePoints.java`），接口检查里专门测了“4096 个 emoji 可以写入、4097 个字符被拒绝”。

**clientIp 为什么是 VARCHAR(45)？** IPv6 带嵌入 IPv4 的最长文本 `ffff:ffff:ffff:ffff:ffff:ffff:255.255.255.255` 正好 45 个字符。`IpAddress.java` 只做格式校验，不做 DNS 解析。

## 5 主键：为什么用 ULID

ULID = 48 位毫秒时间戳 + 80 位随机数，编码成 26 个字符，如 `01M7FF4G8QTH3BJ0CR40MC33VP`。

- **按时间有序**：前 10 位是时间，字符串排序即时间排序。InnoDB 的主键就是聚簇索引，有序主键使插入总发生在 B+ 树末尾，不像随机 UUID 那样到处分裂页面。
- **不依赖数据库**：程序生成，两种数据库用同一个值，接口对外就用它。
- **更短**：26 个字符，32 位 UUID 去掉连字符也要 32 个。MySQL 中再用 `ascii_bin` 保存，每个字符 1 字节；而主键会附在每个二级索引上，主键短，所有索引都变小。

实现见 `Ulid.java`，单元测试用 ULID 规范的示例做了已知值校验。

## 6 时间：统一 UTC

- 程序里用 `Instant`（UTC 时间点）。JSON 输出形如 `2026-11-15T08:00:00.123Z`；传入带时区的时间（如 `+08:00`）会换算成 UTC。
- **MongoDB** 的 BSON Date 本身就是 UTC 毫秒数。
- **MySQL** 的 `DATETIME(6)` 不带时区，存什么就是什么，所以必须固定会话时区：JDBC 参数 `connectionTimeZone=UTC&forceConnectionTimeZoneToSession=true`，再加上 `hibernate.jdbc.time_zone=UTC`。实测 MySQL 中存的是 `2026-11-15 08:00:00.123000`，与 Mongo 的 `ISODate('2026-11-15T08:00:00.123Z')` 一致。
- **精度对齐**：BSON Date 只到毫秒，`DATETIME(6)` 到微秒。`LogService` 统一截断到毫秒，两库存的时间完全一样。

## 7 索引：同一个查询，两边同样的索引

查询：`level = ? AND createdAt ∈ [from, to)`，按 `createdAt DESC, id DESC` 排序，取第 page 页。

| | MySQL | MongoDB |
| --- | --- | --- |
| 复合索引 | `idx_level_created (level, created_at, id)` | `{ level: 1, createdAt: -1, _id: -1 }` |
| 只按时间 | `idx_created (created_at, id)` | `{ createdAt: -1, _id: -1 }` |
| 查看执行计划 | `EXPLAIN SELECT ...` → `Using index condition; Backward index scan` | `.explain()` → `IXSCAN`，没有 `SORT` 阶段 |

要点：**等值条件在前、范围和排序字段在后**，数据库就能沿索引顺序直接取出前 N 条，不需要额外排序。末尾加上 id，是为了时间相同时顺序也确定，翻页不会重复或遗漏。

## 8 写入为什么可能不一样快：持久化策略

| | MySQL（默认配置，本实验未改） | MongoDB 7.0（单机，默认） |
| --- | --- | --- |
| 一次写入 | 一个事务：写 redo log + binlog | insertOne |
| 何时落盘 | `innodb_flush_log_at_trx_commit=1`、`sync_binlog=1`：**每次提交都刷盘**（并发时组提交合并） | 写关注 `w:1`，日志（journal）**约每 100ms 批量刷盘** |
| 宕机风险 | 已提交的数据不丢 | 最近约 100ms 内确认的写入可能丢失 |

所以写入性能对比的不只是“数据库快慢”，还有**持久性承诺的强弱**。报告里结合磁盘写入次数（IOPS）解释这一点。

## 10 JMeter：负载测试与压力测试

**两个概念（ISTQB 定义）**

- **负载测试**：在预期的使用范围内逐级加压，看吞吐量、响应时间怎么变化，找到性能拐点。
- **压力测试**：超出正常负载（或资源受限）时，看系统怎样退化、会不会出错；压力撤掉后能不能**恢复**。

**本实验的设计**

| 类型 | 线程数 | 持续 | 说明 |
| --- | --- | --- | --- |
| 预热 | 50 | 60 秒 | JIT 编译、数据库缓存热身，结果单独保存、不参与比较 |
| 负载测试 | 10、25、50、100 | 各 60 秒 | 从低负载到饱和 |
| 压力测试 | 200、300、400 | 各 60 秒 | 远超饱和点（4～8 倍） |
| 恢复检查 | 10 | 60 秒 | 紧接 400 线程之后，与负载测试的 10 线程结果对比 |

**几个必须知道的细节**

- **线程数 ≠ 每秒请求数**：线程是不停循环的“虚拟用户”，吞吐量 = 线程数 ÷ 平均响应时间。
- **预热非常重要**：同一个服务冷启动后 50 线程只有约 790 次/秒，预热后 400 线程可达 3300 次/秒（`results/` 的预试验记录）。
- **JMeter 5.6 的“持续时间”从每个线程启动时开始算**；线程创建得慢时，实际并发会低于设定值。因此统计时区分“全程”和“稳态”（所有线程都在跑的时间段）。
- **压测机自己也会成为瓶颈**：JMeter 机器的 CPU、内存同样纳入 Prometheus 监控。CDWY3 只有约 550MB 可用内存，`run-test.sh` 显式把 JMeter 堆限制为 400MB（默认 1GB 会启动失败）。
- **JTL 是每个请求一行的原始记录**：本实验关掉了 URL 等用不到的字段，控制文件大小。

## 11 Prometheus：指标从哪来、怎么看

| 来源 | 关键指标 | 说明 |
| --- | --- | --- |
| node-exporter（每台机器） | `node_cpu_seconds_total`、`node_memory_MemAvailable_bytes`、`node_disk_*` | 计数器类型，用 `rate()` / 增量计算每秒值 |
| Spring Boot Actuator + Micrometer | `http_server_requests_seconds_count/sum/bucket`、`jvm_*`、`process_cpu_usage` | 服务端看到的请求数和处理时间，可与 JMeter 结果互相核对 |
| HikariCP / Mongo 驱动 | `hikaricp_connections_active`、`mongodb_driver_pool_checkedout` | 连接池占用和排队，判断瓶颈是否在数据库连接 |

**三种指标类型**：counter（只增不减，如请求总数）、gauge（当前值，如线程数）、histogram（分桶计数，可算 P95/P99）。

**本实验怎么取数据**：现有 Prometheus 开启了 basic auth。我们没有用账号密码调用 API，而是复制一份 TSDB 快照，用 Prometheus 自带的 `promtool tsdb dump` 离线导出（`deploy/scripts/prom-export.sh`），再按每次测试的稳态时间段汇总（`tools/analyze_prom.py`）。

## 12 Docker Swarm 部署要点

- **节点标签决定调度**：`node.labels.lab4_role == mongo` 让 MongoDB 只跑在 CDWY5；两套服务沿用实验三的 `lab3_role == app`（CDWY1）。
- **overlay 网络**：同一网络（`javaee-proxy`）里的服务可以直接用服务名互访，例如应用连 `lab_mysql:3306`、`lab4_mongo:27017`。
- **端口发布**：默认 ingress 模式会经过 Swarm 的负载均衡；本实验用 `mode: host`，直接在 CDWY1 上监听，压测请求少一跳。
- **Docker secret**：数据库密码放在 secret 里，容器内以文件 `/run/secrets/...` 出现，不进镜像、不进仓库。
- **坑 1：Swarm 服务名带下划线**（如 `lab4_logjpa`）。用作 HTTP 主机名时，Tomcat 认为它不是合法主机名，直接返回 400，所以 Prometheus 改用 `IP:端口` 抓取。
- **坑 2：新节点加入 Swarm**。CDWY5 原先与其他 4 台不在同一安全组，2377/7946/4789 端口不通。改安全组后才能加入。加入后，全局服务 node-exporter 会自动调度到新节点，但镜像只在各节点本地，要先把镜像传过去。

## 13 安全与可复现

- 仓库里**没有任何密码**：MySQL/Mongo 应用账号的密码在服务器上随机生成，只存在 CDWY1 的 `/root/.config/lab4/`（权限 600）和 Docker secret 里。
- 应用账号**最小权限**：MySQL `lab4app` 只有 `SELECT, INSERT`；Mongo `lab4app` 只有 `find, insert`。
- MongoDB **不发布端口**，只有 overlay 网络里的服务能访问。
- **数据可复现**：`tools/gen_data.py` 用固定随机种子生成数据，两台数据库服务器各自生成后逐条比对摘要，结果完全一致（`results/00-环境与一致性/`）。

## 14 怎样从数据得出结论（本实验的分析方法）

1. **先看错误和正确性，再看快慢。** 两个阶段共 99 次测试、约 6,237 万个请求，错误率都是 0；45 次写入测试都核对“HTTP 201 的个数 = 数据库新增行数”，全部相等。数据不对，性能数字就没有意义。
2. **用两个来源互相核对。** JMeter 是客户端视角，Prometheus 里的 `http_server_requests_seconds_count` 是服务端视角，第二阶段 63 次测试两者的每秒请求数偏差不超过 0.5%，说明统计口径可靠。
3. **确认压测机不是瓶颈。** 线程数 ÷ 吞吐量 = 每个线程发一次请求的周期，减去平均响应时间，就是 JMeter 自身在两次请求之间花的时间（统计表里的 `client_gap_ms`），正常时不到 0.2 ms。过载测试 800 线程的第一次，这个值是 577 ms：压测机自己占满了 CPU，结果作废重测。
4. **找瓶颈看“谁先到 100%”。** 主对比查询时，MySQL 服务器 CPU 先满（99%），应用服务器约 86%；MongoDB 版正好相反，应用服务器 98%，MongoDB 服务器只有约 66%。
5. **比较效率看“每个请求花多少 CPU”。** CPU 时间（毫秒）= 核数 × 使用率 ÷ 每秒请求数。查询时 MongoDB 数据库端约为 MySQL 的 56%（0.35 对 0.61 ms），应用端两者接近。这比只看吞吐量更能说明“谁更省”。
6. **写入差距要结合磁盘看。** MySQL 写入时每秒写盘约 2,200 次、每条日志约 10 KB：每次提交都要刷盘。MongoDB 默认 w:1 每秒只写盘 35 次、每条约 1 KB；改成 j:true 后每秒写盘升到约 1,500 次，吞吐量却只降 2%：100 个并发写入共享同一次日志同步（组提交）。所以差距不只是“放宽了持久性”。
7. **多轮看波动，并找出波动的来源。** 主对比 3 轮的吞吐量变异系数为 0.5%～3.1%。查询波动大一些，原因是查询前没有重置数据库：每种实现各有一轮的库里留有上一项写入的约 100 万条日志，那一轮低 3%～6%。
8. **过载看退化方式和恢复。** 600～1000 线程时两者都没有报错，而是排队变慢，平均响应时间 ≈ 线程数 ÷ 吞吐量；撤掉压力后，10 线程恢复检查的吞吐量回到基线的 91%～98%。

## 15 第二阶段用到的几个概念

- **固定统计区间**：每次测试 240 秒，只统计第 60～240 秒。前 60 秒包含升压和 JIT、缓存、连接池的预热波动；固定区间让每次测试的统计口径完全相同，便于多轮比较。
- **重复 3 轮看稳定性**：用变异系数 CV = 标准差 ÷ 均值 衡量；CV 小（例如 <5%）说明结果可复现，两种实现的差距大于这个波动才有意义。
- **写关注（write concern）**：MongoDB 的 `w:1` 表示主节点在内存中应用写入后即确认；加上 `j:true` 表示等写入记入磁盘日志（journal）后才确认，持久性与 MySQL `innodb_flush_log_at_trx_commit=1` 对齐。本实验用开关 `LOGDEMO_MONGO_JOURNAL` 切换，对比“默认配置”和“同等持久性”两种情况下的写入性能。
- **并发量不是越大越好**：吞吐量到顶后，再加线程只会排队变长；“最佳并发量”取吞吐接近最高、P95/P99 更低且稳定的档位。
- **连接池不是越大越好**：2 核数据库同时只能真正执行少量语句，连接太多会增加上下文切换和锁竞争；HikariCP 的经验公式“连接数 ≈ 核数 × 2 + 磁盘数”在这里只有个位数。连接池调优就是验证这一点。
- **过载测试要换更大的压测机**：1000 个 JMeter 线程需要较多内存，CDWY3 内存紧张（还运行着别的服务），因此过载实验把 JMeter 放在 CDWY4，并同时监控压测机自身的 CPU，确认瓶颈不在压测端。
- **长时间测试放在服务器上跑**：`nohup` 忽略挂断信号，`setsid` 让进程脱离登录会话，SSH 断开、客户端关机都不影响。再配合“已完成就跳过”的续跑设计，中断后重新执行同一命令即可接着跑。
- **服务器之间的免密登录要收窄**：`authorized_keys` 里一行公钥前可以加选项，`from="172.31.1.19"` 只允许从这个地址登录，`no-port-forwarding` 等禁止转发；临时密钥用完即删。
- **不要原地覆盖正在执行的 shell 脚本**：bash 边读边执行，文件被改写后，正在运行的实例会从原来的字节位置继续读新内容，可能执行到半行命令。新版本先写到别处，停掉旧实例后再替换（或写新文件再 `mv`，旧实例仍读原来的文件）。
- **JMeter 的结果文件是追加写入**：`-l samples.jtl` 遇到已有文件会接在后面写，重跑同一目录前要先删掉旧文件，否则统计会混入上次的数据。
- **连接池的实际连接数可能少于设定值**：HikariCP 的 `hikaricp_connections` 指标显示，MySQL 版连接池多次只有 73、58 个连接，空闲时最低 24 个，之后逐个补足。应用通过 Swarm 服务名（虚拟 IP，由内核 IPVS 转发）连接 MySQL，IPVS 默认会静默断开空闲约 15 分钟的 TCP 连接，连接池要等到使用时才发现；连接池关闭这些连接时 MySQL 也收不到，旧会话会一直占着连接数，最后把共用 MySQL 的 300 个连接全部占满。解决办法是让空闲连接定期有流量：给 HikariCP 设 `keepalive-time`（本组设为 5 分钟，环境变量 `SPRING_DATASOURCE_HIKARI_KEEPALIVETIME=300000`），设好后连接数稳定在 100 个。
- **高并发下 JPA 链路对应用服务器 CPU 更敏感**：MySQL 版查询超过 50 线程后，多数时候吞吐量降到 2,000～2,500 次/秒，此时瓶颈从数据库服务器转到应用服务器，每个请求的应用端 CPU 增加 60%～90%；MongoDB 版没有这种情况。
- **binlog 会占满磁盘**：MySQL 开着 binlog（`sync_binlog=1`），每条写入都会记一份。本实验几十次写入测试累计产生约 14 GB binlog，默认保留 30 天。共享的数据库要留意磁盘空间，清理（`PURGE BINARY LOGS`）前要确认没有别的用途依赖它们：`SHOW REPLICAS` 没有从库、PROCESSLIST 中没有 `Binlog Dump` 线程、没有账号有复制权限、没有备份任务。清理只删日志文件，不改表数据；稳妥起见先用 `mysqldump --single-transaction` 备份相关的库。
